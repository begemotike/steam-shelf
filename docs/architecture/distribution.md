# Distribution

Steam Shelf is distributed outside the Mac App Store as a Developer ID-signed, notarized zip, with in-app updates from Sparkle 2. The Xcode project is not checked in: `project.yml` is the source of truth and XcodeGen generates `SteamShelf.xcodeproj` for every build. A single script, `scripts/release.sh`, archives, re-signs Sparkle's nested helpers, notarizes, staples, signs the zip for Sparkle, updates `appcast.xml`, tags and publishes a GitHub release. The app runs in the App Sandbox with a small set of entitlements, two of which are *temporary exceptions* (one for reading the Steam client's manifest folder, one for Sparkle's installer services).

## Responsibilities

- Define the targets, build settings and dependencies (`project.yml`), the Info.plist content and the entitlements.
- Keep a stable code-signing identity in every configuration (Keychain access depends on it).
- Ship updates safely: EdDSA-signed appcast, notarized and stapled builds, correct nested signatures.
- Keep version numbers monotonic.
- Provide developer conveniences: `Makefile`, the icon generator and local test/screenshot helpers.

## How it works

### `project.yml`

| Setting | Value |
|---|---|
| Project name, bundle prefix | `SteamShelf`, `net.outofajam` (app bundle id `net.outofajam.SteamShelf`, tests `net.outofajam.SteamShelfTests`) |
| Deployment target | macOS 15.0 (`MACOSX_DEPLOYMENT_TARGET` and `LSMinimumSystemVersion`); the minimum for `RealityView` on macOS (Q18) |
| Language | `SWIFT_VERSION: "6.0"`, `SWIFT_STRICT_CONCURRENCY: complete` |
| Signing (base) | `CODE_SIGN_STYLE: Manual`, `DEVELOPMENT_TEAM` set to the developer's team (value in `project.yml`) |
| Versions | `MARKETING_VERSION: "0.1.0"` and `CURRENT_PROJECT_VERSION: "1"` as defaults; the release script overrides both on the command line |
| Other | `ENABLE_USER_SCRIPT_SANDBOXING: YES`, `DEAD_CODE_STRIPPING: YES`, `COMBINE_HIDPI_IMAGES: YES`, `ASSETCATALOG_COMPILER_APPICON_NAME: ""` (the icon is a plain `AppIcon.icns` resource, not an asset catalog) |
| XcodeGen options | `createIntermediateGroups`, `generateEmptyDirectories` |
| Packages | Sparkle (`sparkle-project/Sparkle`, from 2.10.0); `zstd` (`facebook/zstd`, from 1.5.7), product `libzstd` (used by `LarianFormats`) |
| Targets | `SteamShelf` (application; sources `Sources/` plus `Resources/AppIcon.icns` in the resources phase; dependencies Sparkle and libzstd) and `SteamShelfTests` (unit-test bundle, sources `Tests/`, hosted in the app via `TEST_HOST`/`BUNDLE_LOADER`, `GENERATE_INFOPLIST_FILE`) |
| Scheme | `SteamShelf`: builds the app and (for test) the test target; run and test use Debug; code coverage off |

Because `*.xcodeproj` is in `.gitignore`, `xcodegen generate` must run before any build; every `make` target does it. The checked-in `Resources/Info.plist` and `Resources/SteamShelf.entitlements` are regenerated by XcodeGen from the `info:` and `entitlements:` blocks, so edit `project.yml`, not the generated files.

### Build settings per configuration (signing)

| | Debug | Release |
|---|---|---|
| `CODE_SIGN_IDENTITY` | `Developer ID Application` | `Developer ID Application` |
| `ENABLE_HARDENED_RUNTIME` | `NO` (the test bundle must be injectable into the host app) | `YES` |
| `OTHER_CODE_SIGN_FLAGS` | none | `--timestamp` (required for notarization) |

**Why Debug is Developer ID signed.** The Steam and AI keys live in the login keychain, whose item access is tied to the app's signing identity. With ad-hoc signing every rebuild produced a new identity and macOS asked for the keychain password again ("Always Allow") after each build; signing Debug with the same Developer ID as Release makes the identity stable across rebuilds (commit "Sign Debug builds with Developer ID so the Keychain stops re-prompting"). This **supersedes** Q10 in the decision log and the "Debug stays ad-hoc" line of its Sparkle notes. The trade-off is that building Debug now needs the certificate in the keychain. `AppModel` additionally never reads the Keychain at launch (it mirrors "has key" in `UserDefaults`).

### Entitlements (`SteamShelf.entitlements`)

| Entitlement | Why |
|---|---|
| `com.apple.security.app-sandbox` | The app is sandboxed. |
| `com.apple.security.network.client` | Steam Web API, CDN art, Sparkle feed, AI services. No server entitlement. |
| `com.apple.security.files.user-selected.read-write` | Export/Import panels and the Steam-folder open panel. |
| `com.apple.security.files.bookmarks.app-scope` | Persist the user's grant of the Steam folder (needed to read game saves) across launches via a security-scoped bookmark. *Added after release 0.2.3.* |
| `com.apple.security.temporary-exception.files.home-relative-path.read-only` = `/Library/Application Support/Steam/steamapps/` | **Temporary exception.** A read-only peek at `libraryfolders.vdf` and `appmanifest_*.acf` so the open box can say Play versus Install and find the game's bundle. Read-only and limited to `steamapps`; saves under `userdata` are *not* covered by it and require the user's explicit folder grant. |
| `com.apple.security.temporary-exception.mach-lookup.global-name` = `$(PRODUCT_BUNDLE_IDENTIFIER)-spks`, `...-spki` | **Temporary exception.** Lets the sandboxed app talk to Sparkle's installer launcher and status XPC services, per Sparkle's sandboxing guide. Pairs with `SUEnableInstallerLauncherService`. |

Temporary exceptions are generally not acceptable for Mac App Store review; that is fine here because distribution is by Developer ID and GitHub.

### Sparkle

| Aspect | Detail |
|---|---|
| Version | Sparkle 2.10 or later via SwiftPM |
| Feed | `https://raw.githubusercontent.com/begemotike/steam-shelf/main/appcast.xml` (the file `appcast.xml` at the repo root). raw.githubusercontent caches for up to about five minutes, so a fresh release can take that long to appear. The repository must be public for other people's copies to reach the feed and the downloads. |
| Downloads | zips attached to GitHub releases: `https://github.com/<repo>/releases/download/v<version>/SteamShelf-<version>.zip` |
| Signing keys | EdDSA key pair generated with Sparkle's `generate_keys`. The **private key lives in the login keychain** (item "Private key for signing Sparkle updates"); the public key is `SUPublicEDKey` in `project.yml`. Back it up with `generate_keys -x <file>` before replacing this Mac: losing the private key orphans every installed copy, because they would refuse updates signed with a new key. |
| Checks | Automatic once a day (`SUScheduledCheckInterval` 86400) plus **Steam Shelf > Check for Updates...**; Sparkle shows its own UI |
| Sandbox | The installer runs through the documented XPC service: `SUEnableInstallerLauncherService` plus the `-spks` and `-spki` mach-lookup exceptions. Verified: the Release archive launches sandboxed with Sparkle and no XPC errors |
| Alternative | Q19 asks whether to move the feed to the sprucetools.com site on Cloudflare instead of GitHub raw; default GitHub (zero extra hosting) |

### `scripts/release.sh` step by step

Usage: `scripts/release.sh X.Y.Z [--dry-run]`. One-time setup: `xcrun notarytool store-credentials steam-shelf-notary --apple-id <your id> --team-id <your team>` (needs an app-specific password). Strict mode: `set -euo pipefail`.

1. **Validate.** Version must match `X.Y.Z`. For a full release the git tree must be clean and tag `vX.Y.Z` must not exist (a dry run skips both checks).
2. **Build number.** `git rev-list --count HEAD`: always rising, which Sparkle needs because it compares `CFBundleVersion`.
3. **Prepare.** `xcodegen generate`; `xcodebuild -resolvePackageDependencies -derivedDataPath build` (this also fetches Sparkle's command-line tools into `build/SourcePackages/artifacts/sparkle/Sparkle/bin`); abort if `generate_appcast` is missing.
4. **Archive.** `xcodebuild archive` in Release with `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` overridden, into `build/release/<version>/SteamShelf.xcarchive`.
5. **Re-sign Sparkle's nested helpers.** Xcode leaves Sparkle's XPC services, `Autoupdate`, `Updater.app` and the framework signed with *Sparkle's* certificate, which notarization rejects. The script re-signs them, **inside out**, with `codesign -f --timestamp -o runtime --preserve-metadata=entitlements -s "Developer ID Application"`: `Installer.xpc`, `Downloader.xpc`, `Autoupdate`, `Updater.app`, `Sparkle.framework`, and finally the app. `--preserve-metadata=entitlements` keeps the entitlements the helpers already carry.
6. **Verify signatures.** `codesign --verify --deep --strict`; each nested binary and the app must show `Authority=Developer ID Application` (checked with `codesign -dvv`; the pipeline avoids `grep -q` under `pipefail` after an earlier failure).
7. **Zip.** `ditto -c -k --keepParent` (preserves bundle structure and symlinks).
8. **Notarize** (skipped in a dry run). `notarytool submit --wait`, output tee'd to `notarize.log`. **Gate:** unless the log contains `status: Accepted`, the script prints the notary log (first 40 lines) and exits non-zero; nothing is published after a rejection.
9. **Staple.** `stapler staple` on the app, re-zip (so the stapled ticket is in the shipped zip), `spctl --assess --type execute` as a final Gatekeeper check.
10. **Appcast.** Copies the zip (and the existing `appcast.xml`) into a staging folder and runs `generate_appcast` with `--download-url-prefix` pointing at the future GitHub release assets and `--link` to the releases page; it signs the zip with the EdDSA key from the login keychain and merges the new item into the feed. Copies the result back to `appcast.xml`.
11. **Dry run stops here.** `appcast.xml` is left modified (`git checkout appcast.xml` to discard).
12. **Publish (tag ordering).** Commit `appcast.xml` as "Release X.Y.Z (build N)", create tag `vX.Y.Z`, `git push origin main vX.Y.Z`, and only *then* `gh release create vX.Y.Z <zip> --title "Steam Shelf X.Y.Z" --generate-notes`. The tag is pushed first so the release attaches to the existing tag instead of creating its own (the script's comment; the ordering was introduced in the commit "push the tag before creating the GitHub release"). Note the order: the appcast commit is pushed before the release asset exists, so the feed can briefly point at a download that is not there yet.

Releases so far: 0.1.0 (build 10), 0.2.0 (15), 0.2.1 (19), 0.2.2 (21), 0.2.3 (23). Shelf-Keeper notes, the Steam-folder bookmark entitlement, the libzstd package, the ATS local-networking key and the Debug signing change are committed but not yet in a release.

### `scripts/make-icon.swift`

`swift scripts/make-icon.swift out.png` draws the 1024 x 1024 icon procedurally (walnut bookcase, two shelves of glossy boxes using the placeholder-cover palettes, brass nameplate "STEAM SHELF", 2007-style gloss, inside the macOS squircle). The PNG was converted to `Resources/AppIcon.icns` (iconset in `build/AppIcon.iconset`); `project.yml` bundles the `.icns` as a resource. Q12 (no icon in v1) is superseded. Details: [scripts](../reference/scripts.md).

### Build tools (not in git)

`build/` is git-ignored and holds derived data, release outputs (`build/release/<version>/`: zip, archive, appcast staging, `notarize.log`), the resolved Swift packages (including Sparkle's tools), logs and screenshots, plus a set of small local helpers in `build/tools/` used while developing and verifying the UI:

| Helper | Purpose |
|---|---|
| `bt.sh [name]` | Regenerate the project, run the tests, print a one-screen summary of errors, warnings and the test result |
| `run.sh out.png [args]` | Kill any running copy, launch the Debug app with `--demo` (plus extra args), activate it and screenshot the window |
| `shot.sh out.png`, `sized.sh W H out.png` | Screenshot the app window by window id; resize the window with AppleScript first |
| `winid.swift`, `all.swift`, `inid.swift` | Find the app's window id and bounds (Core Graphics window list) |
| `click.swift`, `drag.swift`, `dragpath.swift` | Synthesize mouse clicks (with click count), drags and multi-point drags with holds (used to test drag-to-reorder and dwell page flips) |
| `swipe.swift` | Synthesize a phased horizontal trackpad scroll gesture (used to test `SwipeMonitor`) |

These are compiled binaries beside their sources; they are developer conveniences and are not reproducible from the repository. Other ignored directories: `build/ci` (a second derived-data tree) and `build/signcheck` (an archive and appcast staging folder used to inspect a signed build).

### Versioning rules

- Release versions are strictly `X.Y.Z` (`release.sh` enforces the pattern); `MARKETING_VERSION` in `project.yml` is only the default for local builds.
- `CURRENT_PROJECT_VERSION` (the Sparkle-compared build number) is the git commit count, so it only rises. **Never re-release the same version**: the tag must not exist and Sparkle would see no change.
- A release commit is created by the script ("Release X.Y.Z (build N)") and contains only `appcast.xml`.
- The decision log (Distribution notes) is the source for the signing and feed decisions: [Distribution notes (Sparkle + signing, 2026-09-29)](../decisions/OPEN_QUESTIONS.md#distribution-notes-sparkle--signing-2026-09-29).

## Concurrency and isolation

Not applicable to the packaging itself. In the app, `Updater` is `@MainActor` and starts Sparkle only in normal mode. Swift 6 language mode with complete strict concurrency is set for both targets in `project.yml`, so a data race in new code is a compile error.

## Failure modes and how they surface to the user

| Failure | Result |
|---|---|
| Notarization rejected | `release.sh` prints the notary log and exits; nothing is tagged or published |
| Nested helper still signed by Sparkle's certificate | Signature verification step fails before notarization |
| Tag already exists or tree dirty | `release.sh` refuses to start (full release) |
| Sparkle private key lost | Installed copies cannot validate new updates; they must reinstall manually |
| Repo private or feed cached | Users see no update (or see it up to about five minutes late) |
| Keychain re-prompts after a rebuild | Signing identity changed (for example a non-Developer-ID build); stable identity prevents it |
| Plain http AI endpoint other than localhost | Blocked by ATS and by `AIConfig.base` validation |

## Tests

Nothing in `SteamShelfTests` exercises packaging. The release path is verified by the script's own checks (`codesign --verify`, authority check, `notarytool` status, `spctl --assess`) and by launching the archive sandboxed. `make test` is the pre-release gate by convention (the script does not run tests).
